Infrastructure RDS

Windows ServerRDSFSLogixProxmoxActive Directory

Contexte

Projet réalisé en environnement de lab sous Proxmox VE. L'objectif était de simuler une infrastructure RDS complète telle qu'on la retrouve en entreprise, en regroupant plusieurs rôles sur des VMs distinctes, avec les contraintes matérielles d'un environnement de test.

Problématique

Comment permettre à des utilisateurs d'accéder à un environnement de travail centralisé depuis n'importe quel poste, tout en garantissant la continuité de leur profil et la répartition de charge entre plusieurs serveurs de session ?

Objectifs

  • Mettre en place une infrastructure RDS multi-serveurs avec haute disponibilité
  • Centraliser les profils utilisateurs via FSLogix (VHDX sur partage réseau)
  • Sécuriser les accès distants via une RD Gateway dédiée
  • Valider la bascule transparente entre les deux serveurs RDSH

Solution mise en place

L'infrastructure est composée de 4 serveurs Windows Server sous Proxmox :

RD-GWGateway + Connection Broker — point d'entrée unique et répartition de charge
RDSH01 / RDSH02Deux serveurs de session pour la haute disponibilité et le load balancing
AD-FSLOGIXActive Directory ([labo].local), DNS, stockage profils FSLogix et serveur de licences RDS
FSLogixProfils utilisateurs en VHDX montés depuis \\AD-FSLOGIX\FSLogix à chaque connexion

Les collections de sessions sont configurées dans le Gestionnaire de serveur, avec les serveurs RDSH01 et RDSH02 inclus dans la même collection pour la répartition automatique des connexions.

Preuves visuelles

Vue d'ensemble de l'infrastructure RDS — RD-GW, RDSH01, RDSH02, AD-FSLOGIX
Sélection du serveur Broker (Connection Broker) lors de l'installation des rôles RDS
Vue d'ensemble de la collection de sessions — RDSH01 et RDSH02
Éditeur de registre — configuration des clés FSLogix (Enabled + VHDLocations)

Résultats obtenus

  • Connexion RDWeb fonctionnelle via HTTPS depuis un navigateur client
  • Bascule transparente entre RDSH01 et RDSH02 — le profil FSLogix est bien récupéré
  • Les fichiers utilisateur (Bureau, Documents) persistent entre les sessions et les serveurs
  • Serveur de licences activé en mode test pour valider le fonctionnement hors période de grâce

Compétences BTS mobilisées

Serveur FOG – Déploiement PXE

Ubuntu ServerFOG ProjectPXEDHCPSysprepWindows 11

Contexte

Projet réalisé en environnement de lab sur Ubuntu Server 24.04. L'objectif était de mettre en place un système de déploiement automatisé d'images Windows via le réseau, pour permettre la réinstallation rapide de postes en entreprise sans intervention manuelle sur chaque machine.

Problématique

Comment déployer une image Windows 11 sur plusieurs machines d'un réseau de façon centralisée et automatisée, sans nécessiter de support physique (clé USB, DVD), tout en gérant les différences matérielles entre les postes cibles ?

Objectifs

  • Installer et configurer un serveur FOG Project sur Ubuntu Server 24.04
  • Mettre en place un serveur DHCP avec option PXE (next-server)
  • Capturer une image Windows 11 préparée avec Sysprep
  • Déployer l'image sur des VMs aux configurations matérielles différentes

Solution mise en place

Le serveur FOG est installé sur Ubuntu Server à l'IP statique 10.x.y.15/24. Un serveur DHCP isc-dhcp-server est déployé sur la même machine avec les options PXE intégrées. La chaîne de boot utilise undionly.kpxe pour les machines BIOS classique.

FOG ProjectServeur de capture/déploiement d'images via interface web Apache
isc-dhcp-serverDHCP sur ens18, pool 10.x.y.25-30, option next-server pour PXE
SysprepGénéralisation de l'image Windows (suppression SID, pilotes) avant capture
Image typeSingle Disk Resizable — compatible avec disques de tailles différentes

Extrait technique

/etc/dhcp/dhcpd.conf — Configuration DHCP + PXE
default-lease-time 600;
max-lease-time 7200;
authoritative;

subnet 10.x.y.0 netmask 255.255.255.0 {
  range 10.x.y.25 10.x.y.30;
  option routers 10.x.y.254;
  option subnet-mask 255.255.255.0;
  option domain-name-servers 8.8.8.8;
  next-server 10.x.y.15;       # IP du serveur FOG
  filename "undionly.kpxe";       # Boot file PXE BIOS
}

# Préparation Windows avant capture (terminal admin)
# powercfg /h off                 # Désactiver hibernation
# vssadmin delete shadows /all    # Supprimer shadow copies
# sysprep /generalize /oobe /shutdown

Preuves visuelles

FOG Host Management — création de l'hôte avec nom et adresse MAC
💾 FOG Image Management — création de l'image Windows 11 (Single Disk Resizable)
📤 Capture de l'image — hôte associé, tâche de capture lancée depuis FOG

Résultats obtenus

  • Capture d'une image Windows 11 réussie depuis une VM via démarrage PXE
  • Déploiement fonctionnel sur des VMs avec configurations matérielles différentes
  • Sysprep garantit la compatibilité inter-machines (SID unique, pilotes Plug & Play)
  • Interface web FOG opérationnelle pour la gestion des hôtes, images et tâches

Compétences BTS mobilisées

PC Kiosk Public – Windows

GPOWindows 11PowerShellHardeningIdleLogoff

Contexte

Projet réalisé en entreprise pour sécuriser un poste Windows 11 accessible au public. Le poste est utilisé par des visiteurs sans compte nominatif, ce qui impose de restreindre toute modification système et de garantir le nettoyage complet de la session après chaque utilisation.

Problématique

Comment déployer un poste public sécurisé sous Windows 11, qui empêche toute modification du système par les utilisateurs non identifiés, se déconnecte automatiquement après inactivité, et efface toutes les données de session à chaque redémarrage ?

Objectifs

  • Créer un compte Public dédié aux utilisateurs sans privilèges
  • Bloquer l'accès aux outils système via GPO locale (gpedit.msc)
  • Déconnecter automatiquement l'utilisateur après une période d'inactivité
  • Nettoyer intégralement la session (fichiers, cache, navigateurs) au redémarrage

Solution mise en place

Quatre mécanismes complémentaires sont mis en œuvre pour sécuriser le poste :

Compte PublicCompte local dédié sans droits admin, configuré en session auto-login
GPO via gpedit.mscBlocage CMD, Regedit, PowerShell, Gestionnaire des tâches, Panneau de configuration et modifications du bureau
IdleLogoff (Lithnet)Utilitaire open-source qui surveille l'inactivité et déconnecte la session après x minutes
reset-session.ps1Script PowerShell lancé au démarrage de session qui nettoie tous les dossiers et caches utilisateur

Extrait technique

C:\Script-Public\reset-session.ps1
$ProfilePath = "C:\Users\[compte-public]"

# 1. Fermer les navigateurs ouverts
Get-Process msedge,chrome,firefox -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep -Seconds 2

# 2. Vider les dossiers utilisateur
$Folders = @("Desktop","Documents","Downloads","Pictures","Videos","Music")
$Folders | ForEach-Object {
    Get-ChildItem "$ProfilePath\$_" -Force | Remove-Item -Recurse -Force
}

# 3. Supprimer caches navigateurs et fichiers récents
Remove-Item "$ProfilePath\AppData\Local\Microsoft\Edge\User Data" -Recurse -Force
Remove-Item "$ProfilePath\AppData\Local\Google\Chrome\User Data" -Recurse -Force
Remove-Item "$ProfilePath\AppData\Roaming\Mozilla\Firefox" -Recurse -Force
Get-ChildItem "$ProfilePath\AppData\Roaming\Microsoft\Windows\Recent" -Force | Remove-Item -Recurse -Force

# 4. Vider la corbeille
Clear-RecycleBin -Force

Preuves visuelles

⏱️ IdleLogoff — déconnexion automatique après inactivité (Lithnet)
⛔ Hardening GPO — blocage CMD, Regedit, PowerShell, TaskManager, Panneau de config

Résultats obtenus

  • Aucun accès aux outils système (CMD, Regedit, PowerShell, Task Manager) depuis le compte Public
  • Déconnexion automatique après inactivité configurée via IdleLogoff
  • Session entièrement nettoyée à chaque ouverture (historique, téléchargements, cache navigateurs)
  • Journal de nettoyage enregistré dans C:\Script-Public\reset.log pour audit

Compétences BTS mobilisées

B3.2
Configuration de postes — Déploiement Windows 11, compte Public, stratégies locales

Infra Réseau – Portail Captif

VLANDHCPSwitch GrandstreamWiFiPortail captif

Contexte

Projet réalisé en entreprise chez un client. L'objectif était de déployer une infrastructure réseau complète avec un Switch Grandstream 24 ports PoE, des bornes WiFi et un portail captif pour les visiteurs, tout en isolant le réseau invité du réseau interne.

Problématique

Comment permettre un accès Internet aux visiteurs via WiFi, sans qu'ils puissent accéder au réseau interne de l'entreprise, et en leur imposant une page d'authentification (portail captif) avant toute connexion ?

Objectifs

  • Segmenter le réseau via un VLAN dédié aux invités (VLAN 10)
  • Distribuer les adresses IP aux invités via un DHCP configuré sur l'interface SVI
  • Déployer des bornes WiFi PoE managées et les rattacher au VLAN invité
  • Mettre en place un portail captif pour contrôler l'accès Internet des visiteurs

Solution mise en place

Switch Grandstream 24 PoEAlimentation et gestion des bornes WiFi, configuration des VLANs et du trunk
VLAN 10 – InvitésVLAN dédié isolant les visiteurs du LAN interne
DHCP via SVIInterface virtuelle de commutation (SVI) sur VLAN 10 faisant office de passerelle et serveur DHCP
Portail captifPage d'authentification obligatoire avant tout accès Internet pour les utilisateurs WiFi invités

Extrait technique

Configuration VLAN + SVI + DHCP (Switch Grandstream)
# Création du VLAN invité
vlan 10
  name Invites

# Interface SVI — passerelle + DHCP pour le VLAN 10
interface vlan 10
  ip address 192.168.x.1 255.255.255.0
  ip dhcp pool VLAN10-INVITES
    network 192.168.x.0 255.255.255.0
    default-router 192.168.x.1
    dns-server 8.8.8.8

# Port trunk vers les bornes WiFi (PoE)
interface GigabitEthernet 1/0/x
  switchport mode trunk
  switchport trunk allowed vlan 10

Preuves visuelles

Schéma réseau de l'infrastructure — topologie Switch, bornes WiFi, VLAN 10, portail captif

Résultats obtenus

  • Réseau invité totalement isolé du LAN interne via VLAN 10
  • Distribution automatique des IPs aux visiteurs via DHCP sur SVI
  • Portail captif fonctionnel — les invités doivent s'authentifier avant d'accéder à Internet
  • Bornes WiFi alimentées en PoE et managées depuis le switch

Comment automatiser la sauvegarde incrémentale des partages NAS sur deux sites distants, en gérant l'authentification réseau, en journalisant les opérations et en envoyant un rapport de résultat par email via SMTP sécurisé (TLS) ?

Objectifs

  • Copier incrémentalement les partages des deux NAS vers un emplacement local sécurisé
  • Authentifier l'accès aux partages réseau avec des identifiants chiffrés
  • Générer un log horodaté de chaque opération de sauvegarde
  • Envoyer automatiquement un rapport de synthèse par email (SMTP TLS)

Solution mise en place

Robocopy /MIRSynchronisation miroir incrémentale — ne copie que les fichiers modifiés ou nouveaux
Identifiants chiffrésMot de passe NAS stocké chiffré dans un fichier .txt via ConvertTo-SecureString
Logs horodatésFichier de log unique par exécution dans C:\Logs avec timestamp dans le nom
SMTP TLS port 587Envoi automatique du rapport de synthèse par email après chaque sauvegarde

Extrait technique

PowerShell — backup-nas.ps1 (anonymisé)
# === Paramètres généraux ===
$logFolder    = "C:\Logs"
$username     = "[user-nas]"
$passwordFile = "C:\Scripts\pw.txt"

# === Paramètres Email ===
$smtpServer    = "[smtp].[domaine-client]"
$smtpPort      = 587
$emailFrom     = "no-reply@[domaine-client]"
$emailTo       = "infra@[domaine-client]"
$emailSubject  = "Rapport de sauvegarde NAS - $(Get-Date -Format 'dd/MM/yyyy HH:mm')"
$emailUsername = "no-reply@[domaine-client]"
$emailPassword = "********************"   # stocké séparément en prod

# === Lecture du mot de passe chiffré ===
$securePassword = Get-Content $passwordFile | ConvertTo-SecureString
$credential = New-Object System.Management.Automation.PSCredential($username, $securePassword)

# === Dossier de logs ===
if (!(Test-Path $logFolder)) { New-Item -Path $logFolder -ItemType Directory -Force | Out-Null }
$logFile = Join-Path $logFolder "backup_nas_$(Get-Date -Format 'yyyyMMdd_HHmmss').log"

# === Groupes de sauvegardes (2 sites) ===
$sauvegardes = @(
    @{
        Nom     = "[Site-A]"
        Partages = @(
            "\\10.x.x.x\Commun",
            "\\10.x.x.x\Partage-1",
            "\\10.x.x.x\Public",
            "\\10.x.x.x\Sauvegarde",
            "\\10.x.x.x\Scan"
        )
        DestinationBase = "F:\backup-site-a"
    },
    @{
        Nom     = "[Site-B]"
        Partages = @(
            "\\192.168.x.x\Commun",
            "\\192.168.x.x\Partage-2",
            "\\192.168.x.x\Partage-3",
            "\\192.168.x.x\Partage-4"
        )
        DestinationBase = "F:\backup-site-b"
    }
)

$rapport = @()

# === Boucle principale ===
foreach ($site in $sauvegardes) {
    foreach ($source in $site.Partages) {
        $shareName   = ($source -split '\\')[-1]
        $destination = Join-Path $site.DestinationBase $shareName

        if (!(Test-Path $source)) {
            $plain = $credential.GetNetworkCredential().Password
            cmd.exe /c "net use `"$source`" $plain /user:$($credential.UserName) /persistent:no" | Out-Null
            Start-Sleep -Seconds 2
            if (!(Test-Path $source)) {
                $rapport += "[$($site.Nom) - $shareName] Échec connexion"; continue
            }
        }

        if (!(Test-Path $destination)) { New-Item -Path $destination -ItemType Directory -Force | Out-Null }

        robocopy $source $destination /MIR /Z /XA:H /W:5 /R:3 /LOG+:$logFile

        if ($LASTEXITCODE -le 3) { $rapport += "[$($site.Nom) - $shareName] OK (code $LASTEXITCODE)" }
        else                      { $rapport += "[$($site.Nom) - $shareName] Échec (code $LASTEXITCODE)" }
    }
}

# === Envoi rapport email ===
$smtpCred = New-Object System.Management.Automation.PSCredential(
    $emailUsername,
    (ConvertTo-SecureString $emailPassword -AsPlainText -Force)
)
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
$body = "Sauvegarde terminée.`n`nRésultats :`n" + ($rapport -join "`n") + "`n`nLog : $logFile"
Send-MailMessage -From $emailFrom -To $emailTo -Subject $emailSubject `
    -Body $body -SmtpServer $smtpServer -Port $smtpPort -Credential $smtpCred -UseSsl

  • Rapport email reçu après chaque exécution avec le statut de chaque partage
  • Logs horodatés permettant une traçabilité complète des opérations
  • Robocopy /MIR garantit une copie miroir exacte avec gestion des suppressions
